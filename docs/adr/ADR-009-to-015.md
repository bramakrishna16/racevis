# ADR-009: Source snippets cached by file:line, assigned to all accesses

**Status:** Accepted  
**Date:** 2026-04

## Context

Each race event has two accesses (`accessA`, `accessB`), each with a stack frame pointing to a file and line number. For write/write races (e.g. `counter++`), both accesses point to the same file:line.

## Problem

Early implementation used a `seen` map to skip files already read. For write/write races where both accesses point to the same location, `accessB` was skipped — leaving it with `nil` snippet. The source panel showed "Source not available" for one side.

## Decision

Cache snippets by `file:line` key, but assign the cached result to every access that references that location:

```go
cache := make(map[string]*source.Snippet)
getSnippet := func(file string, line int) *source.Snippet {
    key := source.Key(file, line)
    if s, ok := cache[key]; ok {
        return s // cached — may be nil for stdlib
    }
    s := source.ReadSnippet(file, line, 5)
    cache[key] = s
    return s
}
```

## Trade-offs

- Each unique file:line is read from disk once (correct caching)
- Each access that references that location gets the snippet (correct assignment)
- Slightly more memory — snippets stored once per unique location, referenced by multiple accesses
- The correct trade-off: correctness over micro-optimization for a tool reading a handful of source files

# ADR-010: Stdlib source files excluded from snippet reading

**Status:** Accepted  
**Date:** 2026-04

## Context

Map races and channel races show stdlib internals as the innermost stack frame:
- `runtime/map_faststr.go:161` for map concurrent access
- `runtime/chan.go` for channel races

The source panel was attempting to read these files and showing them alongside user code.

## Decision

Exclude files whose paths contain any of:
- `/usr/lib/go`
- `GOROOT`
- `runtime/`
- `runtime_`
- `maps/runtime`
- `/libexec/src/`
- `go/src/internal`

## Reasoning

Stdlib internals are not useful for debugging user code. Developers need to see their own code (`broker_test.go:81`), not the Go map implementation. Stdlib files may also not be present on all systems (stripped Go installations).

## Trade-offs

- If a genuine race occurs inside stdlib code (unusual), no source is shown
- The stack frame file:line is still visible in the tooltip and left panel
- The filter is path-prefix based — a user file accidentally matching a pattern would be excluded (unlikely in practice)

# ADR-011: All test-attributed goroutines included in visualization

**Status:** Accepted  
**Date:** 2026-04

## Context

Early versions only included goroutines that appeared in race events. Safe tests (`TestNoRace_*`) had no race events, so their goroutines were never added to the visualization. Clicking `TestNoRace_AtomicCounter` showed an empty timeline.

## Decision

Include any goroutine whose creation stack was attributed to a `TestXxx` function, regardless of race involvement:

```go
for gid, info := range tr.Goroutines {
    if info.Creation != nil && info.Creation.TestName != "" {
        relevant[gid] = true
    }
}
```

## Reasoning

The tool's value comes from showing the contrast between safe and racy code. A developer should be able to click `TestNoRace_AtomicCounter` and see 50 clean green ECG lines — proof that the atomic implementation is correct — then click `TestCounterRace` and see the same pattern with red collision zones.

## Trade-offs

- More goroutines rendered — 149 instead of ~20 in the demo suite
- The grouping system handles this by showing each test's goroutines separately
- Runtime internals (GC, timer, sysmon) without test attribution are still excluded

# ADR-012: `annotateLanes` uses map pre-pass over nested loops

**Status:** Accepted  
**Date:** 2026-04

## Context

`annotateLanes` needed to assign collision IDs to each goroutine lane. The initial implementation used a nested loop: for each lane, scan all collisions.

## Decision

Build a `gidToCollisions` map first, then do a single pass over lanes:

```go
gidToCollisions := make(map[uint64][]int)
for _, c := range tl.Collisions {
    gidToCollisions[c.GoroutineA] = append(gidToCollisions[c.GoroutineA], c.RaceEventID)
    gidToCollisions[c.GoroutineB] = append(gidToCollisions[c.GoroutineB], c.RaceEventID)
}
for i := range tl.Lanes {
    tl.Lanes[i].CollisionIDs = gidToCollisions[tl.Lanes[i].ID]
}
```

## Reasoning

The nested loop is O(lanes × collisions). With 149 goroutines and 26 collisions that's 3,874 iterations — acceptable now but would hurt at scale (Cloudflare-scale: 50,000 goroutines × 1,000 collisions = 50 million iterations).

The map approach is O(collisions + lanes) with one extra allocation.

## Trade-offs

- One map allocation per `Correlate()` call
- Negligible memory overhead
- Correct algorithmic complexity for production use at scale

# ADR-013: Frontend is single-file vanilla JS, no framework

**Status:** Accepted  
**Date:** 2026-04

## Context

The visualization UI needs: a test list sidebar, an animated ECG timeline, playback controls, a source code panel, and tooltips.

## Decision

All HTML, CSS, and JavaScript in one file (`ui/index.html`). No npm, no build step, no framework.

## Reasoning

The tool must work immediately after `go run .` with zero frontend setup. A React or Vue app would require:
- `npm install` (downloads ~200MB of dependencies)
- A build step (`npm run build`)
- A separate dev server or bundled output

This contradicts the tool's design goal: instant race visualization with a single command. The UI is complex enough to write in vanilla JS but not so complex that a framework adds meaningful value.

## Trade-offs

- No type safety in JavaScript
- No component reuse patterns — similar UI patterns duplicated across functions
- Harder to test UI logic in isolation
- All acceptable for a developer tool; the backend (Go) is the complex part

# ADR-014: SVG ECG lines instead of div-based bars

**Status:** Accepted  
**Date:** 2026-05

## Context

Goroutine timelines needed to show state (running, runnable, waiting) as colored sections, reveal progressively as the playhead advances, and turn red at collision zones.

Initial implementation used absolutely-positioned `<div>` elements — one per segment per goroutine.

## Problem

With 149 goroutines and ~10 segments each, that's ~1,490 DOM elements. The playhead reveal pattern (`seg.classList.toggle('revealed', sp <= pct)`) iterated all of them on every animation frame (~60 times/second) = ~89,400 DOM operations per second. Measurable jank on large trace files.

## Decision

Render each goroutine as an SVG `<polyline>` inside a `1000×32` viewBox. The playhead update builds a points string and sets it once per goroutine:

```javascript
trace.setAttribute('points', pts.join(' ')); // one string, one DOM write
```

## Reasoning

SVG polylines reduce the per-frame DOM writes from O(segments × goroutines) to O(goroutines). For 149 goroutines: from ~1,490 DOM operations per frame to 149 string assignments per frame — a 10x reduction.

The `1000×32` viewBox with `preserveAspectRatio="none"` handles all scaling automatically — no coordinate math needed when the browser resizes.

## Trade-offs

- SVG coordinate math is less intuitive than CSS percentage positioning
- Two polylines per goroutine (green trace + red collision overlay) adds slight complexity
- The performance improvement justifies the complexity

# ADR-015: Playhead reveal pattern for segments

**Status:** Accepted  
**Date:** 2026-05

## Context

The initial design showed all goroutine segments pre-rendered at full opacity when the page loaded. With 149 goroutines, the timeline was overwhelming — all states visible simultaneously with no sense of temporal ordering.

## Decision

Segments start invisible. The playhead advances left-to-right and reveals segments as it passes their start timestamp. For SVG implementation: the polyline `points` string grows as the playhead advances, building the trace incrementally.

## Reasoning

The reveal pattern transforms the timeline from a static data dump into an animation that mirrors the actual execution. Developers can watch goroutines come alive, run, block, and collide — in the order they actually happened. This is the core UX insight: understanding concurrency requires seeing it unfold in time, not all at once.

The slow-motion feature (0.25× speed) is only meaningful because of the reveal pattern — it lets developers watch the exact sequence of goroutine activations leading up to a collision.

## Trade-offs

- More complex playhead logic — must track `startPct` per segment
- The `⏭` (fast-forward) button jumps to t=1.0 which reveals all segments immediately — equivalent to the old static view
- CPU cost: building polyline point strings on every animation frame. Benchmarked at <1ms per frame for 149 goroutines — acceptable
